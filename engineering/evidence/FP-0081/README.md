## Design

`MemoryBudget` wraps the backing allocator.
It counts the requested byte lengths, refuses an allocation, resize, or remap that would grow the count beyond the limit before the request reaches the backing allocator, and never refuses a shrink or a free.
`Engine.create` builds a budget, allocates the engine record through it, and moves the budget into the record, so the record and the accounting state count against `options.max_allocated_bytes`.
`Engine.destroy` releases the record through a copy of the budget and asserts that the count is zero.
`fp_engine_create` passes the process allocator, and `createEngine` passes a test allocator, so every Zig and C engine goes through the same budget.
The native `Options.max_allocated_bytes` defaults to `std.math.maxInt(u64)`, so the laboratory's engines keep their behavior without a change.

The contract requires that a refused call change nothing that `fp_engine_get_memory` reports.
On the base, a load grew the event queue and then the request map in place, so a refusal of the second growth left the first one allocated.
Each operation now grows at most one container in place, as its last reservation.
`createDocument` and `load` reserve every other growth in new storage (`reserveDeque` and `reserveMap`) and install it only after every reservation succeeded.
A failed operation releases that storage through `errdefer`.
`respond` copies the body before it grows the input queue.
The engine module comment states the rule.

## Resolved ambiguities

1. Amendment 2 requires a padding-free schema, but the FP-0021 case 5 fixture `kind_fixture` put a 64-bit `request` at offset 44 with 4-byte pointers.
   The fixture gains a second handle field, `parent`, so its pointer-sized members are even in number; the case checks the same kinds.
2. FP-0021 case 6 asserted that `engine_options` is 16 bytes.
   The frozen interface adds an 8-byte field, so the expectation is now 24, with a comment that names FP-0081.
   FP-0050 case 11 runs case 6 and passes with it.
3. FP-0021 case 13 requires every owner function in the wrong-thread scenario with at least two calls.
   `fp_engine_set_memory_limit` has no invalid argument other than a null engine, which cannot reach the thread check, so its second call passes a different valid limit.
   The scenario's owner first sets the limit to `UINT64_MAX - 1`, so either foreign limit call would be visible.
4. The C smoke test cannot read queue capacities.
   Its limit run fills the input queue with rejections until a rejection at the limit fails, and it fills the event queue with empty-URL reloads at the limit, because after two unlimited loads such a reload allocates only when the event queue must grow.
   The Zig limit run uses the same procedure through the C symbols.
5. A failed attempt "changes nothing" when the allocated bytes, the zero-budget step's ready events and queued-input flag, and the state and body of each scenario document are unchanged.
   The Zig run also compares the native document, request, input, and event counts.
6. The first `c-abi` before-run could not reach the C file, because the library build compiles the staged test blocks of `src/c_api.zig`.
   A second staged tree with only `tests/c/abi_smoke.c` changed gives the C before-run.
7. `raw/generate.log` holds two rounds, because amendment 2 changed the schema after the first round.
   The first round cannot be renamed with an `-attempt-1` suffix without deleting or overwriting it, so `record` appended the second round.

## Reviews

`reviews/review-1-accept.json` and `reviews/security-review-1-accept.json` accept the task with notes only.

- The limit counts the bytes the engine requests, not the resident memory of the process, and allocator granularity can make resident use larger; it is a local integrity bound, not containment.
  `FP-0099` adds that statement to `api/README.md`.
- A refused `fp_engine_create`, `fp_document_create`, or `fp_document_load` still advances the process-wide owner and identifier counters, which no reported value shows.
- A foreign-thread call that races with `fp_engine_destroy` reads a freed record, as every owner function already does; a handle is valid only until its destruction, and the Rust wrapper's thread bounds in `FP-0029` keep a safe caller from that race.
- `reserveDeque` and `reserveMap` copy into new storage, so a load needs headroom for the whole new buffer under a tight limit.
- The C smoke test cannot observe request or input counts, so the Zig limit run covers them.
